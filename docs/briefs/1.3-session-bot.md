# Brief 1.3: DuelSession, in-memory loopback, bot

**Goal.** One player's side of a match (`DuelSession`), a loopback transport that joins two sessions in one process, and a bot that plays through a session exactly as a remote human would. After this task a complete best-of-three match can run headless on a fake clock, with both sides ending in the same state, including under simulated network lag. This is the heart of the multiplayer design, so correctness matters more than brevity.

export type SessionEvent =
  | { type: 'planted'; player: PlayerId; strike: Strike; index: number }
  | { type: 'judged'; player: PlayerId; index: number; grade: Grade; offsetMs: number | null }
  | { type: 'rejected'; reason: 'stamina' | 'slotTaken' | 'full' | 'notYourTurn' | 'offBeat' }
  | { type: 'phrase'; phase: 'attack' | 'defend'; attacker: PlayerId; phrase: number }
  | { type: 'actOver'; winner: PlayerId; act: number }
  | { type: 'matchOver'; winner: PlayerId }

  constructor(opts: DuelSessionOptions);
  readonly state: DuelState; // current reducer state (getter)
  inputOffsetMs: number;
  /** Call every frame. Emits commit / auto-miss / resolve when the clock passes their boundaries. Safe to call late: it catches up. */
  update(): void;
  /** A click at play-area fraction (x, y), stamped `time` on the clock. Plants or parries depending on whose turn it is. */
  pointerDown(x: number, y: number, time: number, touch: boolean): void;
  view(): DuelView;
  on(cb: (e: SessionEvent) => void): Unsubscribe;
  dispose(): void; // unsubscribe from the transport; further calls do nothing

## DuelSession behaviour

State starts as `initialDuelState(tunables, firstAttacker, firstPhrase)`. `bpm` for the reducer is `grid.bpm`. All boundaries below are computed with `src/core/beat.ts` from `clock.now()`.

**Local attacker** (`state.phase === 'attack'`, `state.attacker === localPlayer`):
- `pointerDown`: `adjusted = time - inputOffsetMs/1000`; `ns = nearestSlot(grid, adjusted)`. If `ns.phrase !== state.phrase`, emit `rejected: notYourTurn`. Otherwise build the strike `{slot: ns.slot, x, y}` with x and y clamped to 0..1, check `plantError` (map `stamina`, `slotTaken`, `full` to the same reasons; anything else to `notYourTurn`), apply `plant`, send `{t:'plant'}`, emit `planted`.
- `update`: when `now >= phraseStart(state.phrase + 1)`, apply `commit` and send `{t:'commit', phrase, strikes}`.

**Local defender** (`state.attacker !== localPlayer`). The defend phrase is `D = (state.phase === 'attack' ? state.phrase + 1 : state.phrase)`.
- The commit from the attacker may not have arrived when the clock enters the defend phrase (network lag), yet the first target can be due immediately. So the defender judges its clicks against the strikes it already knows from `plant` messages **whether or not the commit has arrived**. While `state.phase` is still `attack`, the resulting parry events (including auto-misses) are held in a pending queue instead of being applied; when the `commit` message arrives and is applied, the queue is flushed in order (each one applied to the reducer and sent). Strike indexes are stable because an attacker's plants always arrive in increasing slot order. A strike must not be judged twice (track pending judgements).
- `pointerDown` (only when the clock is inside phrase `D` or within `missWindowMs` before its start): for each unjudged strike compute `offsetMs = (adjusted - slotTime(grid, D, strike.slot)) * 1000` and `judgeParry(...)`; among the non-null results pick the strike with the smallest `|offsetMs|`. If there is one: apply-or-queue `parry`, send (or queue) `{t:'parry'}`, emit `judged` with `offsetMs`. If none, do nothing (a stray click is not an error).
- `update`: every unjudged strike with `now > slotTime(grid, D, slot) + goodWindowMs/1000` becomes an auto-miss (`judged` with `offsetMs: null`). When `state.phase === 'defend'` and `now >= phraseStart(state.phrase + 1)`: apply `resolve` and send `{t:'resolve', phrase, results}` (results after the resolve, i.e. with misses filled in, taken from the pre-transition bookkeeping).
- If the local player is neither (wrong turn), `pointerDown` emits `rejected: notYourTurn`.

**Incoming messages** (ignore every message type not listed):
- `plant`: apply `plant`; if the reducer returns the same reference, ignore it; else emit `planted`.
- `commit`: if `msg.strikes` differs from `state.strikes` (deep compare), replace the state's strikes and results with the message's (results all null) and emit `desync`. Apply `commit`. Flush the pending queue.
- `parry`: apply; emit `judged` (`offsetMs: null`).
- `resolve`: apply any results in `msg.results` that are still null locally as `parry` events first (emitting `judged`), then apply `resolve`.
- `state` (guest only; the host ignores it): compare with the snapshot this session saved immediately after applying the resolve of the same phrase (keep the last such snapshot, keyed by `lastActEndPhrase`/`phrase`). If they differ, adopt the host's state and emit `desync`. Never adopt blindly when equal: the guest may already have planted new strikes since.

**After any applied `resolve`** (local or remote): emit `actOver` when `lastActEndPhrase` changed, `matchOver` when the phase became `matchOver`; if `localPlayer === 0`, send `{t:'state', state}`. Save the snapshot for the comparison above.

**`phrase` events:** emit `{type:'phrase', phase, attacker, phrase}` whenever the reducer's phase/phrase changes through commit or resolve (not on matchOver).

**Catch-up:** `update()` loops until no more boundaries are due (bounded to a sane number of iterations), so a tab that was asleep for several phrases commits and resolves its own overdue phrases at once.

**`view()`** returns a fresh `DuelView` (see `types.ts`) computed from the state and the clock:
- `matchOver` if the state says so.
- Before `phraseStart(state.phrase)`: `countIn` when within `countInPhrases` phrases of it, otherwise `intermission`; `countInBeatsLeft` = whole beats remaining (ceil) in both cases; strikes and targets empty.
- Otherwise the phase follows the state, except for the lag cases: state `attack` but the clock is already past the end of `state.phrase` shows `defend` (targets from the known strikes, results from the pending queue); state `defend` but the clock is past the end of `state.phrase` shows `attack` with the roles flipped and no strikes.
- `attacker` and `localActive` match the phase shown. In `defend`, `targets` holds one `TargetView` per strike with `timeToHit` relative to `now` and its result (applied or pending); `strikes` holds the same strikes. In `attack`, `strikes` is the planted list and `targets` is empty.
- `clockPhrase`, `slotPosition`, `beatPosition` come from `positionAt`. `players`, `act`, `actWins`, `lastActWinner`, `matchWinner` come from the state.

## Bot behaviour

`BotDriver.update()` reads `session.view()` and the clock.
- **Attacking:** at the start of each of its attack phrases it plans once: pick a count in the `strikes` range, choose that many distinct slots, and give each a position from a seeded random walk inside x 0.12..0.88, y 0.15..0.85 (steps of roughly 0.15 to 0.45 width so stamina cost varies). When the clock reaches a planned strike's slot time it calls `session.pointerDown(x, y, slotTimeExactly, false)`. Rejections (stamina) are simply ignored.
- **Defending:** for each target it decides once, when the target first appears: with probability `accuracy` it will parry, with a timing error drawn inside the Bravo window (share `bravoRate`) or between the Bravo and Good windows (rest), sign random, always safely inside the window (use 80% of the window width); otherwise it does not click. When the clock reaches `slotTime + error` it calls `pointerDown(strike.x, strike.y, slotTime + error, false)`.
- The random generator is a small seeded PRNG (for example mulberry32) inside `bot.ts`. No `Math.random`, no timers, no `Date`.

`createBotOpponent().update()` calls the bot session's `update()` and then the driver's `update()`.

## Tests

Use `FakeClock`, a grid of 120 BPM with `startTime` 0, `firstPhrase` 1 (one count-in phrase), and step the clock in 1/60 s frames calling `update()` on both sides (and `pump()` when lag is simulated).

`loopback.test.ts`: synchronous delivery and ordering; deep copy (mutating the sent object afterwards does not change what was received); blobs with meta and a final progress of 1; latency mode delivers only after `pump()` at the right time; close propagates; unsubscribe works.

`session.test.ts` (two sessions on a loopback pair): scripted clicks plant strikes on the right slots; the other side sees them; a full turn with perfect parries leaves health untouched and takes Bravo stamina off the attacker; unparried strikes auto-miss and cost health; roles swap and stamina regenerates; a scripted act where one side never parries ends with the right act winner, an intermission, and the other player attacking first; a whole match reaches `matchOver` on both sides with deep-equal states; **the same scripted match with 150 ms and with 350 ms latency in each direction ends in deep-equal final states identical to the zero-latency run** (this exercises the pending queue: include a strike in slot 0 so the first target is due before the commit arrives); the host sends `state` after each resolve and the guest emits no `desync`; a forged differing `state` message makes the guest adopt it and emit `desync`; `view()` phases across count-in, attack, defend, intermission and matchOver, `countInBeatsLeft`, `localActive`, target `timeToHit`; `rejected` reasons; `inputOffsetMs` shifts judging; catch-up after the clock jumps several phrases; `dispose` stops reacting.

`bot.test.ts`: `createBotOpponent` against a second `BotDriver` driving the host session plays a complete match on the fake clock to `matchOver` with deep-equal states on both sides; the same seeds give the same result twice; accuracy 1 never loses health; accuracy 0 loses every act; the bot never plants more strikes than stamina allows (no negative stamina).
