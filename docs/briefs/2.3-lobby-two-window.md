# Brief 2.3: rooms in the app, and the two-window check

**Goal.** Two people can play each other: create a room, share the link, both ready up, the duel starts in sync, a rematch works, and leaving is handled. Then prove it without people: a Playwright test opens two pages joined by the tab loopback, scripts pointer input on both, plays a full act and checks both pages agree. Screens stay plain (the final design is the next milestone) but must be complete and correct.

**Read first:** `CLAUDE.md`, `docs/ARCHITECTURE.md`, `docs/NETWORKING.md`, `docs/briefs/2.1-pairing-room.md` (the Room and pairing API you consume), then `src/net/room.ts`, `src/net/pairing.ts`, `src/net/codes.ts`, `src/net/broadcastLink.ts`, `src/net/trysteroLink.ts`, `src/net/netConfig.ts`, the existing `src/app/`, `src/scenes/`, `src/ui/`, `src/debug/`, and `tests/e2e/` with `playwright.config.ts`.

**Files you own:** `src/app/**`, `src/scenes/**`, `src/ui/**`, `src/debug/**`, `src/main.ts`, `src/style.css`, `index.html`, `tests/e2e/**`, `playwright.config.ts`, and unit tests for anything pure you add. Do not edit `src/core`, `src/net`, `src/audio`, `src/input`, `src/stage/duelRenderer.ts` internals beyond what wiring needs; if one of those has a bug, work around it minimally and report file and line.

## App behaviour

- **Params** (`src/app/params.ts`): add `net: 'peer' | 'tab'` from `?net=tab` (default `peer`). `tab` uses `createBroadcastLink`; `peer` uses `createTrysteroLink(code, netConfigFromEnv(import.meta.env))`. The room code comes from `roomCodeFromUrl`.
- **Title**: "Create a room" makes a code with `generateRoomCode()`, puts it in the address bar with `history.pushState` (path `/CODE`, keeping the query string), and opens the lobby as host. "Join a room" reveals a code field; a valid code opens the lobby as guest; an invalid one shows "That doesn't look like a room code." If the page was opened with a room code in the URL, the title shows "Join room CODE" as the main button instead (the click is also the user gesture that resumes audio). The display name field stays; an empty name becomes "Player". Both buttons call `engine.resume()`.
- **Lobby scene** (`src/scenes/lobby.ts`): builds link, pairing transport and `Room`. Shows: the room code; the share link (`roomLink(location.origin, code)`) with a "Copy link" button (Clipboard API, falling back to selecting the text); the two players' names; a status line driven by the transport state and room events: "Connecting…", "Waiting for a friend to join", "NAME joined", "Waiting for the host", "This room is full" (with a "Back to title" button), "Your friend is using a different version. Both of you should reload the page."; each player's Ready state; a "Ready" toggle; for the host a "Start" button enabled only when both are ready; for the guest "Waiting for the host to start"; the round-trip time once synced; "Leave" (calls `room.leave()` and returns to the title, restoring the address bar to `/`). If creating the link fails (Trystero import or join throws), show "Could not connect. Check your internet connection and try again." with a retry.
- **Starting**: on the room's `start` event build a `MatchSetup` (`localPlayer`, both names, the room's transport, the `StartInfo` grid, first attacker, first phrase) and go to the duel scene. Music for now is the generated click track at the theme's tempo, scheduled with `engine.playLoop` at `grid.startTime` on each side (the theme screen arrives in a later milestone). `dispose` stops the music but does not close the room. `rematch()` calls `room.requestRematch()` and resolves with the next setup when the room emits `start`.
- **Victory**: after pressing "Rematch" in a room match show "Waiting for your friend…"; if the friend already asked, say "NAME wants a rematch". "Back to title" leaves the room.
- **Leaving**: if the transport closes in the lobby, the duel or the victory screen, show "Your friend left" and return to the title (address bar back to `/`).
- **Debug overlay**: show transport state, role, the room's round-trip time and clock offset. When the host edits a tunable during a room match, send `{ t: 'tunables', tunables }` so the guest follows (check that `Room` applies a `tunables` message at any time; if it only does so before start, report it and apply it in the scene instead).
- **Scripted input for tests** (debug mode only): `window.__ttt.script(events)` where each event is `{ phrase: number, slot: number, x: number, y: number, offsetMs?: number }` (absolute phrase index, play-area fractions). Each frame, for every event whose clock time `slotTime(grid, phrase, slot) + offsetMs/1000` has been reached, dispatch a real `pointerdown` (and `pointerup`) `PointerEvent` on the stage element at the matching client coordinates, so the click goes through the real input path. Also expose `window.__ttt.room`, `window.__ttt.grid` and `window.__ttt.events` (an array of the session events seen, capped at 500).

## The two-window check (`tests/e2e/two-window.spec.ts`)

Two pages in the **same browser context** (BroadcastChannel needs it), both with `?net=tab&debug=1`. Console errors, warnings and page errors on either page fail the test.

1. **Room flow**: page A creates a room with name "Ada"; read the code from the page; page B opens `/CODE?net=tab&debug=1` with name "Bo" and joins. Assert each page shows the other's name. A third page opening the same code sees "This room is full" and the first two are undisturbed. Close the third.
2. **A full scripted act**: the host page's URL carries `tunables={"startHealth":30}` and `bpm=140` (confirm the guest adopts both). Both press Ready, the host presses Start. Before the first attack phrase, install scripts on both pages: turn 1 the host plants 2 strikes and the guest parries one and leaves one; turn 2 the guest plants 2 and the host parries both; turn 3 the host plants 3 and the guest parries one, which brings the guest to 0 and ends the act. Assert on both pages after the act: act winner is player 0, `actWins` is `[1, 0]`, healths at the end of the act were 30 and 0 (read from the session events or state before the next act resets them; capture the `actOver` event and the last `state`), and `JSON.stringify(session.state)` is identical on both pages at a quiet moment. No `desync` event on either page. Save screenshots of both pages mid-duel and of the lobby into `test-results/screens/`.
3. **A whole match and a rematch**: continue the script (or let `autoplay` drivers take over through a debug hook) until `matchOver`; both pages show the same winner's name; both press Rematch; a new count-in starts on both and the first attacker has flipped.
4. **Leaving**: close page B mid-lobby and mid-duel (two short tests); page A shows "Your friend left" and returns to the title.

If background pages are throttled in headless Chromium (requestAnimationFrame stops on the page that is not in front), add the launch flags that prevent it (`--disable-renderer-backgrounding`, `--disable-background-timer-throttling`, `--disable-backgrounding-occluded-windows`) rather than weakening timing assertions.

The real WebRTC path (`net=peer`) cannot be tested here. Make sure it builds and that the lobby reaches "Connecting…" then either pairs or shows the error message; say plainly in the report that it is untested.
