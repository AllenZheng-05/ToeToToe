## What to build

1. **App start-up.** Add `import 'pixi.js/unsafe-eval'` before any other Pixi use (the site ships with a Content-Security-Policy without `unsafe-eval`; check the import path exists in the installed PixiJS 8.23.0). Import the kit fonts and `kit.css`; wait for `fontsReady()` and the theatre textures before the first scene shows (a plain "Loading…" on the mat meanwhile). Open the store once (`openStore()`) and keep it on the `App` (`app.store`).
2. **The stage** (`src/stage/stage.ts`): the theatre from `createTheatre` is always present behind every scene, in the layer order `back`, `middle` (puppets), `front`, then marks, with the DOM overlay above. Scenes can ask for the sign (`setSign`) and sun position. Set `PLAY_RECT` in `layout.ts` to what `docs/DECISIONS.md` item 16 says if it is not already.
3. **Puppets in the duel.** Two `PuppetView`s, player 0 on the left facing right and player 1 on the right facing left, on both players' screens (positions are shared as play-area fractions, so the sides must not flip per viewer). Bases behind the ledge as in the art kit dev page. Each frame pose them with `solveRig`, passing the previous segment count:
   - Local puppet: the tip follows the pointer (`onMove` samples, converted to design pixels, not clamped to the play area but kept on the stage). On touch the tip follows the finger while it is down and stays where it was when lifted. Before any pointer movement: an idle pose.
   - Opponent puppet: the tip eases toward its most recent planted strike or judged target; idle pose otherwise. Ease with a frame-rate-independent factor using the clock delta.
   - Drawings: `MatchSetup` gains `puppets?: [PuppetImagesSource | null, PuppetImagesSource | null]` (define the type in `src/scenes/types.ts` as the three canvases/bitmaps the `PuppetView` needs). When absent: the local player uses `loadSelectedPuppet(app.store)` decoded with `decodeDrawing`; the opponent uses the pink preset (or the teal one if the local player chose pink). A later task fills this field with the drawings received from the other player.
4. **Marks.** Replace the plain strike and target drawing with `MarksView.update(view, tunables, bpm, { touch })`. `touch` is true once the player has used a touch pointer (so the drawn radius matches the judged radius).
5. **HUD** (`src/ui/hud.ts`) rebuilt from the kit, laid out as in mocks 5 and 6: a `playerPlate` at each end of the ledge (inset so the curtain hems do not cover them) with name, Health, Stamina, a "you" tag on the local player's plate, a "Winded" tag; `phraseDots` in the middle of the ledge showing the eight half-beats of the current phrase with the current one lit and the planted or due slots filled; `actCounter` ("Act 2 of 3" and act wins); the `banner` in letter tiles: "ATTACK!" when the local player attacks, "PARRY!" when defending, "WATCH" when it is the opponent's phase to act, the count-in number during a count-in (4, 3, 2, 1 on the beat), "NAME takes the act" in an intermission; `gradePop` pop-ups ("Bravo!", "Good", "Miss") at the target's position for both players' parries; a streak note on tape when the local player's streak reaches 3 or more ("7 in a row!"); a "Not enough stamina" note on `rejected: stamina`; and asides: a typed note with a short heckle from "a child in row G" now and then (on an act ending, a streak of 5, three misses in a row; at most one on screen, gone after a few seconds; write eight or so mild, funny lines).
   Keep every existing `data-testid` and `data-value` (`health-0`, `health-1`, `stamina-0`, `stamina-1`, `banner`, `act-counter`, …) so the browser tests keep passing; if the kit's ids differ, set these on the right elements. The banner element's text content must still read as the plain words (the kit sets an aria-label; make sure the tests can read it, updating the tests to use the accessible name if needed, not weakening what they check).
6. **Sounds** stay as they are.
7. **Debug overlay**: move it so it does not cover a player plate (for example top-left under the valance, collapsible with a small toggle), since screenshots are taken with `?debug=1`.
8. Delete code that is now dead (the plain renderer's shapes), but keep `duelRenderer.ts` as the single place that turns a `DuelView` into stage updates.
