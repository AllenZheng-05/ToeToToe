# Brief 12: fixes from the first real two-device match

**Background.** The game was deployed and played over the real network for the first time: a laptop as host, an iPad (Safari) as guest, no Bluetooth audio. Two problems, diagnosed by the reviewer from the code:

1. **The friend's puppet never arrives** ("Fetching NAME's puppet" stays up). Proven cause: Trystero delivers binary payloads as a `Uint8Array` (`@trystero-p2p/core/dist/action-wire.mjs`, `decodePayload`, and the chunked receive buffer), but `src/net/pairing.ts` near line 40 accepts only `data instanceof ArrayBuffer`, so every blob (drawings and songs, both directions) is dropped silently. Progress events still arrive, so the label shows with nothing behind it.
2. **The host's parry phrase "reloads".** Proven mechanism: when the guest's `commit` reaches the host before the host's own clock reaches the phrase boundary, `onCommit` (`src/core/session.ts` near 388) moves the state to `defend`, phrase P+1, and `view()` (near 478) sees `now < phraseStart(P+1)` and returns a count-in view with no strikes or targets: the marks vanish, a count-in number shows, and at the boundary the targets come back with rings part-closed. The same happens with an early `resolve`. It needs the guest's grid to run early by more than the one-way latency, i.e. the guest's clock-offset estimate is too high. Likely sources in `src/net/room.ts` (inference): the first sync burst starts at `hello`, at the same moment both sides send up to 1.5 MB of drawings on the same ordered channel, so pings queue behind file data; the jump detector (near 557) replaces the whole window with two consecutive disagreeing samples whatever their round trip; nothing re-syncs during a match (pinging stops at `beginMatch`, near 677).

## Part 1: binary payloads

- In `trysteroLink.ts`, normalise what the binary action delivers: accept `ArrayBuffer` or any `ArrayBufferView` (copy the exact byte range: `buffer.slice(byteOffset, byteOffset + byteLength)`), drop anything else; type the action honestly. Keep `pairing.ts` tolerant too (accept a view as well as a buffer) so no link implementation can cause this again.
- When `pairing` discards an invalid or malformed blob (bad metadata, wrong type, over the size limit), it must tell its listeners (an `onBlobRejected`-style event or equivalent, with the meta when known) so `Exchange` clears that transfer's progress at once and that drawing part falls back to a preset part, and a rejected song gives the guest the plain "could not load" path. The label must never stay up with nothing arriving.
- If a `sendBlob` fails or the peer reports nothing received within the existing stall timeout, the drawings are re-sent once (the song already has a retry path); do not loop.
- Tests: a fake Trystero room in the link tests that delivers a `Uint8Array` with metadata (inline size and a multi-chunk size, and a view with a non-zero `byteOffset`) and the blob reaches `Transport.onBlob` byte-for-byte; a rejected blob clears progress and falls back; the re-send. If practical, drive Trystero's real action-wire code over a fake channel in one test so the payload type is pinned to the library; if that is not practical say why.

## Part 2: the view tolerates early messages

Whatever the clock error, a player must never see marks vanish or a count-in appear mid-act because a message arrived ahead of the local beat.

- In `DuelSession.view()`: when `now < phraseStart(s.phrase)` and `s.phrase` is not the act's first phrase, render as the phase that is still running on the local clock: after an early `commit`, the attack phase of the previous phrase continues, with the committed strikes shown as the attacker's strikes (and the defender-to-be's pre-phrase rings in `marks.ts` keep working because they are computed from the local clock); after an early `resolve`, the defend phase continues to its local end with the final results shown. Count-in and intermission views are only for real act starts (and the match start). Work out the exact conditions from the state (`actFirstPhrase`, `phase`, `phrase`) and keep the function pure and readable; no new state unless unavoidable.
- Local input during such a moment must go to the right place: a defender's click before its own phrase has started locally is not a parry of a not-yet-started phrase (it is ignored or handled as an early click exactly as today's rules say for slot 0); an attacker whose commit has not yet gone out is unaffected. Check `pointerDown` paths against the early-state case and add tests.
- The mirror case (messages arriving late: guest's last plants and commit after the defender's phrase has begun) already works through the pending-parry queue; add a test that pins it: targets present from the defender's own clock, late plants appear with correct `timeToHit`, results kept when the commit confirms the same strikes.
- Tests on the fake clock with two sessions whose clocks disagree by +300 ms, +1 s and −300 ms and latencies of 0, 50 and 300 ms: in every case, across a full act, the view never returns `countIn` or `intermission` between an act's first phrase and its end, `targets`/`strikes` are never empty at a moment when the previous frame had them and the phase on the local clock has not changed, and both sessions still end in identical states. Also the existing tests that expect a count-in at act start still pass.

## Part 3: the clock sync

- Do not measure while files are in flight: `Room` gets a way to know transfers are active (inject a predicate or let `Exchange` tell it), discards samples taken then, and takes a fresh burst when transfers end and before `start` (the bounded wait before start already exists; keep it).
- Jump detector: a sample only counts as jump evidence if its round trip is close to the best recent one (for example within 1.5 times, plus a few ms); after a confirmed jump, clear the window and take the estimate from a fresh burst's lowest-round-trip sample rather than from the two samples that triggered it. A suspect sample must not toggle Ready off and on (check the `ready:false` near line 493 and remove the flicker; Ready should drop only on a confirmed jump).
- Keep syncing during a match at a slow rate (for example one ping every few seconds; ordinary timers are fine, this is not beat timing), but apply corrections only in a way that cannot disturb play: do not move the grid mid-act. Record the drift; if the estimate has moved by more than `clockJumpMs` when an act ends, apply the correction at the next act start (both sides must still agree on the grid: work out who owns the correction, the guest translating the host's unchanged grid with its newer offset is the simplest) and re-measure before a rematch as now. If a safe mid-match correction is not possible without a protocol change, only record and display the drift and say so.
- The guest device is an iPad: check `src/audio/engine.ts` for anything that could bias timestamps there (coarse `currentTime` steps, `outputLatency` undefined or changing, the interpolation cap) and make ping timestamps as accurate as the clock allows; if `now()` can lag by up to a step when called rarely, say how large that is and whether a `performance.now()`-anchored interpolation between audio-clock steps (still expressed in audio-clock time, as rule 1 requires) is warranted for sync stamps. Do not change how beats are scheduled.
- Tests: an asymmetric hub (different delay each way, a burst of delayed samples at the start as if behind a file transfer, occasional slow outliers): the offset error stays under half the best round trip plus a few ms; a pair of slow outliers does not move the estimate; a real jump is followed within one burst; Ready does not flicker.
